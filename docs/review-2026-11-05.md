# MC Toolbox 代码检查与功能建议

检查基线为 `main@d7512e1`（v1.12.9）。本次重点是安装失败后的重试、实例副本隔离、桌面 API 和好友文件传输。功能建议基于 2026 年 11 月 5 日查阅的官方资料。下列工作量为工程估计。

## 本轮修复

| 场景 | 原来的行为 | 修复与验收重点 |
| --- | --- | --- |
| 外部网页请求本机启动器 | 本地服务绑定回环地址，但路由接受任意 Host 和跨源简单请求 | 统一入口核对本机地址、实际端口及浏览器来源。覆盖外部 Host、跨源 POST、同源请求与桌面宿主使用的无 Origin 请求 |
| 好友登录、传输 | 客户端收到 HTTP 响应才比较证书指纹，此时令牌或上传内容已经发出。普通文件下载也可能把 404 错误正文写成成功文件 | 有固定指纹时先完成 TLS 核对再发送 HTTP 请求。指纹错误的测试服务器收到 0 个请求；文件接口返回错误时保留已有目标文件 |
| 复制与改名 | 并发复制可能分到同一目录。外部实例复制遇到读写错误会跳过文件，副本改名后仍可能使用旧游戏路径 | 复制前独占目标目录，失败清理本次副本，改名同步其自有游戏目录。覆盖并发同名复制、外部存档隔离和模拟复制失败 |
| 素材安装与服务端包转换 | 首个文件失败后，其余下载可能在界面报错后继续写入。素材线路限流判断反向，转换时吞吐计数没有增长 | 下载池把取消信号传给在途任务，等待清理后报告失败。素材按线路状态控制扩容，Modrinth 服务端包转换按实际接收字节计算吞吐 |
| 给好友补齐模组 | 发送端传入的清单形状与差异比较函数不匹配，相同 JAR 也可能重传。替换时已有同名禁用备份可能影响旧版本保留 | 复用现有模组差异比较和文件命名规则，验证双方一致、版本不同及备份重名三种情况 |
| 启动器读取不完整的设置 | 设置中缺少监测段时，后台初始化监测引擎会异常退出，窗口打不开 | 启动迁移复用设置 API 的合并逻辑，保留自定义选项并补齐默认值。用只含自定义列数的设置文件验证启动与持久化 |

范围说明：实例改名修复作用于本次及以后执行的改名操作。对已在旧版产生且归属不明的历史路径，需要先核实实际存档位置。

在 Windows、Node.js 22.18.0 上执行了一轮完整的 Node 测试，共 318 项，首轮通过 317 项。唯一失败发生在存档编辑器端到端用例启动后台时。修正设置迁移后，定向复测目录管理和存档编辑器两个端到端用例，2/2 通过。本次交付范围为源码与报告，验证使用测试实例及本地模拟服务。

## 后续值得优化的两条路径

| 优先级 | 代码依据 | 建议和验证办法 |
| --- | --- | --- |
| 高，大文件导入 | 实例内容上传路由调用 `readRawBody`，允许 512 MiB。处理时保留所有分块，再用 `Buffer.concat` 生成连续缓冲区。整合包上传已有 `receiveUploadedPack` 流式写入实现 | 抽取已有流式落盘和中断清理逻辑，保留内容上传自己的大小、扩展名、重名校验。在同一台电脑导入同一个大资源包，对比 Node 进程峰值 RSS；中断上传后检查目标目录 |
| 中，长群聊 | 好友服务的 `groupMessagesFor` 首次同步读完整 JSONL，`unreadForGroup` 每次遍历该群历史。好友页每两秒触发一次刷新 | 保留 JSONL 数据格式，先缓存最近消息与每人已读游标，再做向前翻页。用一个有十万条消息的测试群对比首次打开、热刷新耗时和内存占用，并核对未读数。当前判断来自代码路径，尚无生产压测数据 |

## 功能方案与首版验收

### 1. 批量 Mod 更新可撤销 · 优先级高，工作量中

Modrinth App 提供一键更新。MC Toolbox 已经能按哈希批量查更新，但 `startModUpdates` 按项下载、替换。玩家一次更新多个相互依赖的 Mod，中途失败就可能留下新旧混装。可以把撤销能力直接放在现有更新确认框和下载中心里。[Modrinth App 官方功能](https://modrinth.com/app)

- 首版只处理此次涉及的 JAR。复用现有更新列表、下载校验和任务中心，预览旧版与新版，先下载到暂存目录，全部通过校验后替换。记录旧文件、目标路径、启停状态和操作进度，以便重启后恢复或撤销。
- 验收：选三个 Mod，第二项下载失败时原文件哈希全部一致；模拟替换阶段中断，重启后可以恢复；成功更新后点一次撤销，三个文件及原禁用状态都能复原。

### 2. 群聊固定入服配置 · 差异化优先，工作量中

GDLauncher 已用分享码让好友重建实例。MC Toolbox 同时具备群聊、模组比对和开服工具，服主可以直接在群里维护“这个服现在用哪一版”，让后来加入的人也能用同一份说明进服。[GDLauncher 官方功能](https://gdlauncher.com/)

- 首版由群主固定一个带版本号的清单，写明服务器地址、MC 与加载器版本、必装和可选模组。成员选本地实例后复用 `diffManifests`、`fillPlan` 和现有直连启动参数，预览差异并补齐。限制第三方分发的文件沿用手动获取流程。
- 验收：两个已安装实例，其中一个少一个 Mod。前者直接进服，后者只获取缺项。服主升级清单后，成员看到新增、替换和所需下载量，本地可选模组由玩家决定是否保留。

### 3. Prism / MultiMC 实例迁移向导 · 拉新优先，工作量中

目前的 `scanRoot` 识别标准 `.minecraft/versions`，而仓库启动器说明已明确记录 `mmc-pack.json` 的导入边界。Prism 官方的 MultiMC 迁移流程以复制实例为基础，适合作为导入体验参照。[Prism 官方迁移说明](https://prismlauncher.org/wiki/getting-started/migrating-multimc/)

- 首版支持原版和标准 Fabric 组件。读取源实例清单，预估空间，在工具箱内用现有安装器重建版本，再复制模组、配置、脚本和存档。自定义补丁或未知组件在开始写盘前逐项提示。
- 验收：迁移一个含存档与模组的 Fabric 实例，移走源目录后新实例仍可启动；源目录迁移前后哈希一致。覆盖存储空间不足或中途取消的情况。

### 4. 跨实例重复文件分析 · 可独立试做，工作量小起步

XMCL 用硬链接或符号链接复用实例资源。MC Toolbox 已共享 assets 和 libraries，也能整理单个实例中的重复模组。剩余空间可以从不同实例里内容相同的 JAR、资源包入手。[XMCL 官方项目说明](https://github.com/Voxelum/x-minecraft-launcher)

- 首版只提供空间报告。先按文件大小筛选，再复用既有哈希缓存核实内容；区分“内容相同”与“已共享同一物理文件”。玩家能看见哪些实例、哪些文件占用了空间。
- 验收：准备两个相同 JAR、一个同名不同内容的 JAR，以及一对已有硬链接。报告的潜在可释放字节只计算真实重复占用。后续再评估只读资源复用，验证单实例替换文件的隔离性。

建议先交付方案 1，它覆盖每位更新 Mod 的玩家，也能给方案 2 提供失败恢复能力。如果目标是吸引服主和固定联机群，下一项选方案 2；如果优先降低换启动器的成本，下一项选方案 3。
